# Giga To Do

Локальное приложение для работы команды AI-агентов. Четыре доски: **аналитика, фронтенд, бэкенд и тестирование**. Агенты выполняют задачи через Gigacode, независимые критики проверяют результат. В режиме **«Офис»** Pixel Agents показывает текущие запуски как анимированных персонажей.

Стек: **.NET 8, PostgreSQL, React 19 + Vite**. Приложение открывается по адресу **http://localhost:5180**. Оно доступно только с локального компьютера, без внешних CDN. Исполнение агентов по умолчанию выключено.

## Что установить

| Компонент | Когда нужен |
|---|---|
| .NET SDK 8 | Для сборки и запуска сервиса |
| PostgreSQL 17 или совместимый сервер | Всегда: задачи, обсуждения, расписания и запуски хранятся в БД |
| Node.js 22.12+ и npm | Для разработки и пересборки React-интерфейса; при запуске уже собранного интерфейса не нужны |
| Gigacode и его авторизация | Для реального выполнения задач |
| Пользовательские навыки и MCP | Для работы с вашими репозиториями, Jira, дизайном, браузером и другими системами |
| Podman | Необязательно: для запуска PostgreSQL в контейнере вместо локального сервера |

Для первой сборки нужен доступ к разрешённому NuGet-источнику. Для пересборки интерфейса — к npm-источнику либо заранее подготовленному npm-кэшу. Готовые файлы интерфейса находятся в `src/GigaTodo/wwwroot`; React и графика Pixel Agents загружаются локально.

Из корня проекта `dotnet --version` должен показывать **8.0.x**. Версию SDK выбирает `global.json`; установленный SDK 8 может быть любой совместимой feature-ветки, рекомендуется актуальный патч. Сборка проверена на SDK 8.0.427. Решение — `GigaTodo.sln`, совместимое с SDK 8.

EF Core закреплён на 8.0.33, PostgreSQL provider — 8.0.11, Npgsql — 8.0.9. Для работы с миграциями подготовлен локальный инструмент той же версии: `dotnet tool restore`, затем `dotnet ef migrations has-pending-model-changes --project src/GigaTodo`. Для обычного запуска инструмент EF не нужен: миграции применяет сервис.

Для распаковки вложений используется NuGet-пакет SharpCompress 0.50.8 (MIT, поддерживает .NET 8). Установка отдельного архиватора не требуется.

## Быстрый запуск

Команды выполняются из корня репозитория. Примеры для macOS/Linux; вариант PowerShell ниже.

### 1. Подготовить PostgreSQL

К запуску приложения PostgreSQL уже должен работать: локально либо в Podman. Приложение само сервер БД не запускает. Для локального сервера заранее создайте **отдельную базу** и пользователя, имеющего право создавать таблицы. Не указывайте базу другого приложения.

Для варианта с Podman на macOS/Windows сначала подготовьте виртуальную машину командой `podman machine init` (один раз) и запустите её: `podman machine start`. В Linux с локальным Podman виртуальная машина не нужна.

Создайте контейнер PostgreSQL (один раз; команды подходят также для PowerShell):

```sh
cp .env.example .env
# Откройте .env и задайте POSTGRES_PASSWORD.
podman volume create giga-todo-postgres
podman run -d --name giga-todo-postgres --env-file .env -e POSTGRES_DB=giga_todo -e POSTGRES_USER=giga_todo -p 127.0.0.1:5432:5432 -v giga-todo-postgres:/var/lib/postgresql/data postgres:17
podman exec giga-todo-postgres pg_isready -U giga_todo -d giga_todo
```

Дождитесь ответа `accepting connections` от последней команды; при необходимости повторите её. Контейнер при первом запуске с пустым томом создаёт базу `giga_todo` и пользователя `giga_todo`. Порт 5432 открыт только на localhost; если он занят, измените левый порт в `-p` и строке подключения. Данные сохраняются в именованном томе `giga-todo-postgres`. Для последующих запусков используйте `podman start giga-todo-postgres`, затем проверку готовности выше. Изменение пароля в `.env` не меняет пароль уже созданной базы.

### 2. Настроить подключение и запустить

```sh
export ConnectionStrings__Database='Host=localhost;Port=5432;Database=giga_todo;Username=giga_todo;Password=YOUR_PASSWORD'
dotnet restore GigaTodo.sln
dotnet run --project src/GigaTodo
```

Откройте **http://localhost:5180**. При первом запуске сервис сам применит миграции и создаст четыре доски. Пароль должен совпадать с настройками вашего PostgreSQL. В варианте с Podman файл `.env` передаётся контейнеру, а строку подключения приложению нужно передать отдельно.

PowerShell:

```powershell
$env:ConnectionStrings__Database = 'Host=localhost;Port=5432;Database=giga_todo;Username=giga_todo;Password=YOUR_PASSWORD'
dotnet restore GigaTodo.sln
dotnet run --project src/GigaTodo
```

Для остановки приложения нажмите **Ctrl+C** в терминале. PostgreSQL в Podman останавливается командой `podman stop giga-todo-postgres`; данные сохраняются в именованном томе. Локальным сервером управляйте через службу PostgreSQL вашей ОС.

### Настройки в файле

Вместо переменных можно создать игнорируемый Git файл `src/GigaTodo/appsettings.Local.json`:

```json
{
  "ConnectionStrings": {
    "Database": "Host=localhost;Port=5432;Database=giga_todo;Username=giga_todo;Password=YOUR_PASSWORD"
  },
  "Runtime": {
    "Runner": "Disabled",
    "Executable": "gigacode",
    "PublicUrl": "http://localhost:5180",
    "Root": ".runtime",
    "WallTimeSeconds": 900,
    "MaxTurns": 50,
    "MaxToolCalls": 200,
    "MaxConcurrentAgents": 10
  }
}
```

Переменные окружения имеют приоритет. Не публикуйте локальные настройки с доступами. `Runtime__Executable` может содержать абсолютный путь к CLI. Скрипт `./scripts/run-app.sh` запускает тот же сервис с вашей конфигурацией; `GIGA_DOTNET` позволяет указать путь к SDK.

### Автоматическая авторизация Gigacode

Откройте **«Настройки доски» → «Авторизация Gigacode · все доски»**. Введите команду запуска вашего скрипта и нажмите **«Сохранить авторизацию»**. Например:

```sh
bash "/absolute/path/login-gigacode.sh"
```

Для Windows можно указать `powershell.exe -NoProfile -NonInteractive -File "C:\Scripts\login-gigacode.ps1"` или команду запуска `.cmd`. Команда выполняется на компьютере сервиса через `/bin/sh -c` на macOS/Linux или `cmd.exe /d /s /c` на Windows, в корне backend-проекта. Окружение наследуется от приложения. Используйте абсолютные пути; скрипт должен сам проверять/обновлять авторизацию без интерактивного ввода и возвращать код **0** только при успехе. Изменение окружения внутри дочернего скрипта не передаётся Gigacode: авторизация должна сохраняться в его общем хранилище учётных данных.

Скрипт запускает **бэкенд при распознанной ошибке авторизации Gigacode**, включая работу критиков, ответы и resume. Перед обычным запуском он не вызывается. Бэкенд останавливает процесс CLI, выполняет скрипт и **один раз** продолжает ту же сессию через `--resume`. Запуск остаётся в прежней карточке и занимает прежнее место в общем лимите агентов. Одновременные ошибки используют одно успешное обновление общих credentials; скрипты не выполняются параллельно. Пустая команда отключает восстановление. В Disabled/Mock скрипт не вызывается. Сохранение настройки не запускает скрипт. Таймаут — **120 секунд**, можно задать **5–600**; ожидание, авторизация и повтор входят в общий бюджет запуска агента.

Бэкенд анализирует диагностические события CLI `error`/ошибочный `result` и сообщения stderr об истёкших/невалидных credentials, в том числе структурированный код 401. Текст ответов агента и результаты его инструментов не считаются сигналами для авторизации; обычный 403 не запускает скрипт. Если ваш форк выдаёт иной формат ошибки, адаптер нужно уточнить по фактической диагностике. Реальная проверка на установленном Gigacode остаётся отдельной.

При повторной ошибке авторизации, ошибке скрипта или таймауте восстановление прекращается, причина появляется в карточке. Если ID сессии отсутствует и агент уже начал отвечать/работать, после обновления авторизации нужно продолжить задачу вручную. Запуск с нуля разрешён только при отсутствии признаков начала работы. Уже переданный через `submit_result` итог повторно не выполняется. События восстановления видны в истории с автором `backend`; скрипт не передаётся агенту и не предоставляется через MCP-инструменты. Возобновление сессии сохраняет контекст, но после внешнего действия без подтверждённого результата нужна проверка его фактического состояния.

Настройка общая для всех досок, применяется к следующим вызовам скрипта без перезапуска и сохраняется в `Runtime:Root/gigacode-authentication.json` вне Git. Уже начавшийся скрипт использует прежнюю команду. Вывод и команда не включаются в журналы задач, промпты и snapshot агента. Доступы держите внутри защищённого скрипта/хранилища, а в поле задайте только его запуск.

Начальное значение можно задать через `Runtime__AuthenticationCommand` и `Runtime__AuthenticationTimeoutSeconds` либо соответствующие ключи `Runtime` в локальном JSON. Сохранённая через интерфейс настройка имеет приоритет над этими начальными значениями, в том числе при пустой команде; чтобы вернуться к начальным значениям, остановите сервис и удалите только `gigacode-authentication.json`.

## Как пользоваться

### Доски и создание задачи

1. Выберите **«Доски»**, затем нужную команду: аналитику, фронтенд, бэкенд или тестирование.
2. Нажмите **«＋ Новая задача»**. Обязательно только описание: оно станет промптом агента.
3. При необходимости задайте название, критерии готовности, источник, ссылки, зависимости и способ проверки результата.
4. Нажмите **«Создать»**. Карточка появится внизу **To Do**.

Ссылки на Jira, Confluence, репозитории и дизайн агент открывает своими инструментами. Backend приложения не привязан к конкретному внешнему сервису. Одинаковое описание и источник на одной доске возвращают существующую задачу, в том числе завершённую.

### Прикрепление файлов

В форме задачи и повторения есть отдельная кнопка **«📎 Прикрепить файлы»**. Можно выбрать несколько файлов любого типа: документы, изображения, текст, бинарные файлы и архивы. Файлы сначала загружаются и обрабатываются, затем становятся частью задачи при нажатии «Создать»/«Сохранить» — агент не успеет запуститься без них.

В существующей карточке откройте **«Вложения»**, прикрепите файлы и нажмите **«Сохранить вложения»**. Здесь же можно убрать связь с файлом. Во время активного запуска состав вложений менять нельзя; дождитесь окончания или отмените запуск. Изменение вложений само не меняет стадию и не запускает агента. При повторной отправке одинаковой задачи новые вложения добавляются к существующей, если она не выполняется.

ZIP, RAR, 7z, TAR, GZip, BZip2, XZ и поддерживаемые библиотекой варианты распаковываются автоматически. Вложенные архивы раскрываются в подпапки `*.contents`. Кнопка **«Содержимое»** показывает извлечённые файлы; оригинал и каждый распакованный файл можно скачать. Парольные, повреждённые, многотомные без остальных частей и неподдерживаемые варианты получают явную ошибку. Оригинал сохраняется, частичная распаковка удаляется; файл не выдаётся за успешно распакованный.

Вложения шаблона наследуются всеми новыми экземплярами повторения. Изменение шаблона не меняет состав уже созданных задач. Удаление связи с файлом не удаляет общий оригинал или вложения других задач.

По умолчанию: **100 МБ суммарно за загрузку**, до **20 файлов за раз**, до **50 вложений у задачи**. На один архив с учётом вложенных — **512 МБ распакованных данных**, **10 000 элементов**, **3 уровня** и **120 секунд**. Пути за пределами папки, ссылки и перезапись извлечённых файлов не допускаются. Для изменения ограничений используйте переменные:

```sh
Attachments__MaxUploadMegabytes=200 \
Attachments__MaxExpandedMegabytes=1024 \
Attachments__MaxArchiveEntries=20000 \
Attachments__MaxArchiveDepth=4 \
Attachments__ExtractionTimeoutSeconds=180 \
dotnet run --project src/GigaTodo
```

Допустимые диапазоны: загрузка 1–1024 МБ, распаковка 1–10240 МБ, элементы 1–100000, глубина 1–10, время 1–600 секунд. Неизвестные/запрещённые варианты архива остаются доступными в оригинале. Распаковка не запускает вложенные программы или макросы.

Оригиналы, SHA256, статус и пути передаются исполнителю и критику через prompt, `attachments.json` и MCP `get_task`. Содержимое документов и изображений агент изучает своими доступными инструментами; наличие файла не гарантирует наличие нужного инструмента на конкретном компьютере. Реальная проверка Gigacode остаётся отдельной.

Файлы лежат в `Runtime:Root/attachments` (по умолчанию `.runtime/attachments`), метаданные и связи — в PostgreSQL. В backup включайте всю `.runtime`. Загруженные файлы, в том числе оставшиеся после отмены формы, автоматически не удаляются: общие материалы могут использоваться другими задачами. В Git они не включаются.

### Приоритет и зависимости

Очередь выбирается **сверху вниз**. Перемещайте карточки внутри колонки перетаскиванием или кнопками **↑ / ↓**. Переносить карточки между стадиями вручную нельзя.

В поле **«Начать после завершения задач»** можно выбрать задачи любых досок. Пока хотя бы одна из них не в **Done**, задача ждёт, а диспетчер берёт следующую доступную карточку. Циклы и зависимость от самой себя запрещены. Изменить зависимости можно в окне задачи, пока она в To Do и не запущена.

### Стадии и ревью

| Стадия | Что происходит |
|---|---|
| To Do | Задача ожидает своей очереди, завершения зависимостей и свободного агента |
| In Work | Исполнитель работает над задачей |
| In Review | Результат проверяет агент-критик либо человек |
| Done | Результат принят |

Критик может задать исполнителю вопрос, принять результат или вернуть задачу на доработку в низ To Do. По умолчанию после трёх возвратов автоматика приостанавливается; лимит можно изменить в настройках доски.

Если при создании выбран **«Человек»**, карточка выделяется красным. В In Review откройте её и нажмите **«Принять»** либо напишите замечания и выберите **«На доработку»**. Done означает принятие результата, а не автоматический merge или архив внешнего тикета.

### Окно задачи

Нажмите на карточку или персонажа в офисе. Здесь доступны:

- описание, критерии, ссылки и зависимости;
- результат, выполненные проверки и скачивание артефактов;
- сообщение исполнителю или критику;
- дочерние задачи, история событий и запуски;
- приостановка, продолжение и отмена активного запуска;
- сброс сохранённых сессий, когда задача приостановлена или заблокирована.

**«Отменить запуск»** останавливает процесс; завершённые внешние действия не откатываются. Перед повтором проверьте, что агент уже успел сделать. **«Сбросить сессии»** убирает ID продолжения, но сохраняет историю приложения; новый запуск начинается только после команды продолжить.

### Повторяющиеся задачи

Под каждой доской есть таблица **«Повторяющиеся задачи»**.

1. Нажмите **«＋ Создать повторение»**.
2. Заполните задание, интервал в днях и часах, дату первого слота, часовой пояс и дни недели. Общий интервал должен быть положительным.
3. Кнопка **«Будни»** выбирает понедельник–пятницу. **«Ближайшие запуски»** показывает пять будущих слотов.
4. После сохранения доступны изменение, пауза/включение и история.

Дата в форме вводится в часовом поясе браузера; фильтр дней применяется в указанной зоне, по умолчанию Europe/Moscow. Время слота означает **добавление в очередь**, а не гарантированный старт агента. Сетка повторений считается от даты начала: дни недели отфильтровывают слоты без сдвига интервала. Каждый слот создаёт отдельную задачу независимо от готовности предыдущей. После простоя пропущенные слоты записываются в историю, без массового создания накопившихся задач.

### Настройки доски и репозитории

Кнопка **«Настройки доски»** позволяет задать:

- лимиты исполнителей и критиков, число возвратов на доработку;
- модель и режим подтверждений Gigacode;
- дополнительные инструкции исполнителю и критику;
- локальные репозитории, базовые ветки, frontend-команду, локальный URL, API стенда и ссылку на дизайн;
- просмотр матрицы навыков и сценариев.

В **«Репозитории по умолчанию» → «Локальный путь к репозиторию»** укажите абсолютный путь к уже существующему Git-репозиторию **на компьютере бэкенда**. У каждой доски свой список; URL удалённого репозитория сюда не подходит. Задача наследует репозитории доски; флаг **«Задать репозитории вместо настроек доски»** позволяет переопределить список. Включённый флаг с пустым списком означает работу без репозитория.

Для каждого репозитория сервис создаёт изолированный worktree задачи. Повторные запуски и ревью используют ту же рабочую копию. Полные инструкции навыков, авторизация и внешние MCP должны быть настроены в Gigacode отдельно.

### Имена веток по Jira

Исполнитель читает основной Jira-тикет своими инструментами и проверяет его тип:

| Тип Jira | Имя ветки | Пример |
|---|---|---|
| Story | `feature/КЛЮЧ-НОМЕР` | `feature/BIM-123` |
| Bug | `bugfix/КЛЮЧ-НОМЕР` | `bugfix/BIM-456` |

Кавычки, описание и дополнительные суффиксы в имя не добавляются. Исполнитель переименовывает текущую служебную ветку в назначенном worktree через `git branch -m`. Критик проверяет правило, но не меняет ветку. Точный ключ должен присутствовать в описании, поле источника или ссылках задачи.

Если имя уже занято, тип неизвестен, тикет недоступен или основных тикетов несколько, агент запрашивает уточнение. Чужую ветку не удаляет и не переключает. Для других типов сохраняет служебное имя `giga/{taskId}/rN`, пока не задано отдельное правило. Backend проверяет соответствие имени ключу задачи, но не обращается в Jira и не подтверждает фактический тип тикета.

### Офис Pixel Agents

Нажмите **«▧ Офис»** в верхней панели. Здесь видны запуски **всех четырёх досок**:

- работающий исполнитель или критик занимает компьютер;
- критик отмечен отдельной ролью, завершённый запуск освобождает рабочее место;
- нажатие на персонажа или строку справа открывает задачу;
- на этаже 20 мест, дополнительные этажи появляются автоматически;
- завершённые запуски видны ещё до 45 секунд;
- Mock всегда помечен как тестовый режим;
- при потере связи показан последний снимок, анимация приостанавливается.

Используются настоящий Canvas-движок и графика [Pixel Agents](https://github.com/pixel-agents-hq/pixel-agents), закреплённые в репозитории под MIT. Интернет для офиса при запуске не нужен. Технические детали и обновление: [docs/PIXEL_AGENTS.md](docs/PIXEL_AGENTS.md).

Сейчас офис отражает **состояние процесса и роль**. Конкретные чтения файлов, вызовы инструментов и внутренние субагенты Gigacode пока не отслеживаются. Список справа доступен с клавиатуры и на мобильном экране.

## Включение агентов

Переключатель **«Исполнение»** находится в верхней панели:

| Режим | Поведение |
|---|---|
| Выключено | Можно готовить карточки; расписания продолжают добавлять их в очередь |
| Тестовый режим | Mock автоматически проводит задачи по жизненному циклу, без реальной работы |
| Gigacode | Запускает настоящий CLI с вашими навыками, инструментами и разрешениями |

Переключатель действует до перезапуска. Постоянное значение задаётся `Runtime__Runner` или `Runtime:Runner`. Перед включением Gigacode пройдите [docs/GIGACODE.md](docs/GIGACODE.md). На машине без CLI и пользовательских MCP этот режим не станет рабочей интеграцией.

**Mock используйте только с тестовыми карточками:** он может автоматически принять задачи, назначенные агенту-критику. Он не подтверждает готовность кода или внешних интеграций. Отключение исполнения запрещает новые назначения; для остановки уже активного процесса используйте отмену в задаче.

### Общий лимит параллельных агентов

`Runtime__MaxConcurrentAgents` — целое число **1–100**, по умолчанию **10**:

```sh
Runtime__MaxConcurrentAgents=25 dotnet run --project src/GigaTodo
# Либо:
Runtime__MaxConcurrentAgents=25 ./scripts/run-app.sh
```

В PowerShell: `$env:Runtime__MaxConcurrentAgents = '25'` перед запуском.

Лимит общий на все доски, включает исполнителей, критиков и ответы, исключает внутренних субагентов Gigacode. Лимиты отдельных досок также применяются. Изменение переменной требует перезапуска; неверное значение останавливает запуск. Счётчик сверху показывает действующий лимит.

## Разработка React-интерфейса

Исходники — `frontend/src`. Сборка полностью заменяет сгенерированное содержимое `src/GigaTodo/wwwroot`; вручную его не редактируйте.

```sh
cd frontend
npm ci
npm run build
npm test
npm run check:vendor
```

После сборки запускайте .NET как обычно. Для разработки с обновлением страницы:

```sh
# В первом терминале, из корня:
dotnet run --project src/GigaTodo

# Во втором:
cd frontend
npm ci
npm run dev
```

Откройте **http://127.0.0.1:5173**. Vite передаёт `/api` локальному backend на порту 5180, включая SSE. В production Vite не нужен. Зависимости закреплены в `frontend/package-lock.json`; для закрытого окружения подготовьте пакеты в разрешённом npm-источнике/кэше либо перенесите готовый `wwwroot`.

Локальный frontend приложения и frontend целевого проекта — разные вещи. Команда/URL/API стенда целевого проекта задаются у репозитория; агент использует их через свои навыки.

## Проверки

### Приложение и PostgreSQL

```sh
dotnet build GigaTodo.sln
# Независимый набор без настоящего Gigacode:
dotnet test GigaTodo.sln --filter 'Category!=RealGigacode'
```

Без `GIGA_TEST_DATABASE` проверки PostgreSQL явно пропускаются. Для полного локального набора создайте **отдельную тестовую базу**:

```sh
export GIGA_TEST_DATABASE='Host=localhost;Database=giga_todo_tests;Username=giga_todo;Password=YOUR_PASSWORD'
dotnet test GigaTodo.sln --filter 'Category!=RealGigacode'
```

Интеграционные тесты сохраняют записи с тестовыми досками. Не указывайте базу с рабочими задачами.

### Настоящий Gigacode

```sh
dotnet test GigaTodo.sln --filter 'Category=RealGigacode'
# Весь набор, включая реальные интеграционные проверки:
dotnet test GigaTodo.sln
```

Четыре непропускаемые проверки проверяют CLI и флаги, текстовый ответ модели, stream-json/session_id и историю через `--resume`. Они **падают**, если CLI/авторизация недоступны; автоматического skip или подмены на Mock нет. По умолчанию команда — `gigacode` из PATH. Параметры: `GIGA_CLI`, `GIGA_TEST_MODEL`, `GIGA_TEST_TIMEOUT_SECONDS` (10–600, default 180).

Проверки обращаются к модели и используют квоту. Они не требуют запущенного приложения или БД, но не подтверждают все внешние MCP/навыки. На текущем компьютере Gigacode и пользовательское внешнее окружение отсутствуют; эта приёмка остаётся открытой.

### Браузер

Запустите приложение на отдельной тестовой базе:

```sh
cd tests/browser
npm install
npx playwright install chromium
npm test
```

Это отдельные тесты нашего React-интерфейса в Chromium; Playwright не является зависимостью работающего приложения или инструментом Gigacode. Проверяются доски, формы, зависимости, ручное ревью, Pixel Agents, этажи, ошибки связи и мобильный экран. Масштаб 100 персонажей проверяется на явно тестовых UI-данных, не на 100 реальных процессах. URL задаётся `GIGA_TEST_URL`, по умолчанию http://localhost:5180. Тесты создают карточки/расписания, временно включают Mock, в конце выключают его. Скриншоты сохраняются в `artifacts/` рабочего каталога.

Процессный/HTTP MCP-контракт проверяется отдельно через `python3 tests/contract-smoke.py` с `Runtime__Executable`, указывающим на `tests/fixtures/gigacode-contract.py` (Python 3; на Unix файл исполняемый). Это тестовая CLI-фикстура, не настоящий Gigacode. Детали — [docs/GIGACODE.md](docs/GIGACODE.md).

## Если не запускается

- **Ошибка подключения к БД:** проверьте, что PostgreSQL запущен, база существует, хост/порт/пользователь/пароль верны. При первом запуске нужны права на создание таблиц.
- **Требуемый SDK не найден:** установите .NET SDK 8 и проверьте `dotnet --list-sdks`; `global.json` закрепляет семейство 8.0. Для скрипта можно задать полный путь через `GIGA_DOTNET`.
- **Порт 5180 занят:** остановите ранее запущенный экземпляр приложения. На одну базу предусмотрен один диспетчер; второй не получает lease.
- **Пустая страница или старый интерфейс:** пересоберите `frontend` командой `npm ci` и `npm run build`, затем пересоберите/перезапустите .NET и обновите страницу.
- **Нет персонажей:** офис показывает запуски, а не все задачи To Do. При выключенном исполнении и отсутствии недавних запусков офис пуст.
- **Задача не берётся:** проверьте режим исполнения, паузу, блокер, зависимости и лимиты доски/приложения.
- **Gigacode не найден или требует подтверждения:** проверьте `Runtime__Executable`, авторизацию, headless-разрешения и [целевую инструкцию](docs/GIGACODE.md). Не обходите ограничения CLI или MCP.

## Резервные копии и обновление

Перед согласованной копией остановите приложение. Сохраните БД через `pg_dump --format=custom` и каталог `.runtime` с worktree, результатами и сессиями. Восстанавливайте через `pg_restore` в отдельную базу. Пользовательская конфигурация Gigacode резервируется отдельно.

`.runtime` и локальные настройки могут содержать рабочие данные — храните копии приватно. Перед обновлением сохраните backup; миграции находятся в `src/GigaTodo/Migrations` и выполняются при старте.
