# Проверка и подключение Gigacode в целевом окружении

## Что здесь не проверено
На машине разработки нет Gigacode, пользовательских SKILL.md, внешних MCP и доступа к внутреннему стенду. Реализованы адаптер и расширение; ниже — чек-лист проверки после переноса. Оригинальные реестр и конспект пользователя сохранены как исходные материалы, а не список обязательных интеграций.

## Подготовка
- [ ] Выполнить `dotnet test GigaTodo.sln --filter 'Category=RealGigacode'`: четыре непропускаемых теста CLI/help, текстового ответа, stream-json/session_id и восстановления истории через resume. Здесь они красные из-за отсутствия CLI. Пути/модель/таймаут задаются GIGA_CLI, GIGA_TEST_MODEL, GIGA_TEST_TIMEOUT_SECONDS. Зелёный результат не закрывает отдельные пункты MCP/навыков/прав доступа ниже.
- [ ] Создать задачу с документом/изображением и ZIP: настоящий агент читает attachments.json/get_task, оригинал и распакованное содержимое, отражает использованные источники в результате. Проверить права чтения путей вложений в целевом CLI и доступность инструментов для бинарных форматов. Fixture проверяет доставку и чтение файлов процессом, но не возможности модели/внешних навыков.
- [ ] Проверить `gigacode --help`: -p, -o stream-json, --resume, --approval-mode и бюджеты.
- [ ] Проверить модель и реальный доступ к ней. Не назначать неподдерживаемый effort.
- [ ] Установить/связать `extensions/giga-todo` штатной командой из версии CLI (`gigacode extensions link <absolute-path>` описана в конспекте).
- [ ] Убедиться, что видны пять task/frontend-навыков и семь адаптированных Superpowers-навыков. Исходники и LICENSE находятся внутри расширения, ревизия и SHA256 — superpowers.lock.json. Исходные скрипты при установке не исполняются.
- [ ] Не подключать одновременно полный upstream Superpowers с конкурирующими одноимёнными навыками. Обвязка заменяет внутреннюю оркестрацию на наш диспетчер.
- [ ] Проверить личные навыки `~/.gigacode/skills`, проектные инструкции и разрешения. Прочитать полные инструкции до автоматизации; исходные гейты и подтверждения сохраняются.
- [ ] Убедиться, что процесс приложения запущен тем пользователем, у которого настроены CLI, навыки и внешние MCP. Не запускать сервис от другого пользователя с пустым профилем.

## Как запускается задача
Сервис создаёт собственные `.runtime/tasks/<id>/executor` и `critic`. В папке роли записываются `agent-profile.json` (точная матрица и политика из snapshot запуска), `GIGACODE.md` (условные правила выбора навыков), `.gigacode/settings.json` (permissions роли и MCP giga-todo). В settings временно помещается bearer credential конкретного запуска. Права файла 0600 на Unix; после нормального завершения credential удаляется. Общий `~/.gigacode/settings.json` не читается и не переписывается сервисом.

Единый источник конфигурации — `src/GigaTodo/AgentConfig/catalog.json`: восемь профилей, 21 сценарий, 32 навыка и три политики (executor, critic, reply). После изменений запустить `python3 scripts/export-agent-config.py`, затем `--check`. Файлы `extensions/giga-todo/agents/*.md` — восемь named-agent шаблонов; основные процессы всё равно запускает C#-сервис. Не вызывать их дополнительно из основного процесса. Матрица читается в настройках доски кнопкой «Навыки и сценарии агентов», через /api/agents или docs/SKILL_MATRIX.md.

Для подключения в целевой среде подготовлен `scripts/link-extension.sh` (не выполнялся). Для запуска сервиса — `scripts/run-app.sh`, необязательный GIGA_DOTNET задаёт путь к SDK. C#-запуск агентов уже содержит команду, аргументы, бюджеты, отмену и resume; отдельный shell-скрипт на каждую задачу не нужен.

Проверить, что версия CLI объединяет этот project scope с пользовательскими MCP, а не скрывает их. Если объединение отличается, адаптировать GigacodeRunner по фактической документации. Не копировать защищённый глобальный конфиг и не обходить Filesystem Guard. Runtime root не должен быть доступен другим пользователям машины; после аварии старый token отозван в БД, файл очистится при следующем запуске роли.

Рабочие копии репозиториев расположены рядом в `repos/r0`, `repos/r1`; абсолютные пути и конфигурация передаются в задании. CLI должен иметь разрешённый доступ к этим папкам. Сессии executor/critic хранятся отдельно, ExecutorReply продолжает executor. В потоковом выводе ожидается верхнеуровневый `session_id`; проверить это на установленной версии. Если сохранённая сессия недоступна, в окне заблокированной/приостановленной задачи нажмите «Сбросить сессии», затем «Продолжить»: новая сессия получит задание и историю из базы. Автоматического повтора внешних действий при сбросе нет.

## MCP и разрешения
- [ ] Проверить initialize/tools/list/tools/call на http://localhost:5180/mcp из запуска агента.
- [ ] Убедиться в доступности tools через tool_search. Discovery timeout и tools/call timeout различаются.
- [ ] Для нашего MCP настроить необходимые разрешения в поддерживаемом CLI формате; не разрешать автоматически все внешние серверы.
- [ ] Headless не поддерживает интерактивные диалоги. Проверить чтение/правку, сборку, тесты и git в доверенном worktree. auto-edit не считать разрешением всех shell-команд.
- [ ] При недоступном разрешении агент должен вызвать request_clarification; иначе процесс завершится с блокировкой/по бюджету, и приложение предложит продолжение.
- [ ] Проверить подготовленные permissions критика и ExecutorReply: запрет штатной записи, изменяющих Git-команд, default approval mode независимо от auto-edit доски. В named-agent шаблонах дополнительно задан disallowedTools. Это конфигурация, а не проверенная OS-изоляция; фактические имена инструментов и действия внешних MCP нужно подтвердить в целевой версии. При необходимости настроить дополнительные ограничения на стороне CLI.

## Контрольные поручения
1. Без репозитория: прочитать описание и передать краткий результат через submit_result.
2. Создать две разные задачи одного внешнего источника; повторное одинаковое описание возвращает существующую.
3. Критик задаёт вопрос; исполнитель отвечает; критик возвращает на доработку и принимает новую версию.
4. С репозиторием: исправление и тест в отдельном worktree. Проверить commit/push/PR/MR средствами агента по разрешениям проекта. Merge не автоматический.
5. Перезапуск: прерванный запуск не продолжается автоматически; проверить ранее выполненные внешние действия и возобновить по ID.
6. Frontend: локальный сервер, API КСУП БИМ https://ksup-bim.ift.delta.sbrf.ru/bim/api, SberBrowser devtools, сценарии, console/network, сравнение с доступным дизайном и скриншоты в файлы. Не использовать этот API как default других проектов.
7. Браузер: acquire_resource browser перед действиями, release_resource после. Блокировка — кооперативная для подключённых агентов; внешние процессы вне приложения ей не управляются.

Зафиксировать версии CLI, расширения, пользовательских навыков, доступные инструменты и фактические результаты в PROGRESS. Недоступные проверки оставить незакрытыми.
