# План Giga To Do

## Продукт
Локальное приложение одного пользователя: ASP.NET Core .NET 8, EF Core/Npgsql и PostgreSQL, React 19 + Vite. Исходники frontend, production-сборка в wwwroot. HTTP API, SSE и Streamable HTTP MCP. Внешние сервисы и доступы остаются в окружении Gigacode.

Четыре независимые доски: аналитика, фронтенд, бэкенд, тестирование. Колонки To Do → In Work → In Review → Done. Новая карточка внизу; выбор сверху вниз с пропуском незавершённых зависимостей. Только перестановка внутри колонки. Возврат на доработку — в низ To Do. Ручное ревью красное с текстовой меткой.

Обязательно только описание. Заголовок по первой строке; доска текущая; ревью агентом; зависимости не заданы; репозитории из настроек доски (можно явно очистить). Необязательные критерии, источник и ссылки. Модальное окно: задача, результат, артефакты, ссылки, обсуждение и история.

## Выполнение
Начальные лимиты: два исполнителя и один критик на доску. Общий лимит Runtime__MaxConcurrentAgents (1–100, по умолчанию 10) активных запусков на всех досках, включая критиков и ответы, без внутренних субагентов Gigacode. Атомарное назначение под общей блокировкой PostgreSQL. Задача ждёт Done всех своих зависимостей; заблокированные карточки пропускаются сверху вниз. Зависимости любых досок, без циклов и самоссылок; редактируются только в To Do. Ревью независимо. Критик спрашивает, принимает или возвращает; сам не исправляет. Три возврата приостанавливают автоматику. Человек может продолжить.

Gigacode запускается напрямую через Process/ArgumentList, `-p` и `-o stream-json`; бюджеты и разрешения настраиваются. Возобновление строго `--resume ID`, отдельно по роли. Без safe/bare/YOLO и без предположения о поддержке интерактивных подтверждений. Сначала тестовый исполнитель; затем проверка установленного CLI.

Git: отдельная ветка и worktree задачи для каждого репозитория, повторная работа в том же окружении. Без репозитория — отдельная папка. Агент сам делает commit/push/PR/MR по правилам проекта. Done не означает merge или архивацию.

Jira-ветки: после чтения тикета своими инструментами исполнитель переименовывает текущую служебную ветку: Story → feature/KEY-123, Bug → bugfix/KEY-123. Точный ключ без кавычек и суффиксов. При коллизии имени, неясном типе, недоступном тикете или нескольких основных тикетах — уточнение. Чужую ветку не переключать и не удалять. Для остальных типов сохраняется служебное имя. Критик проверяет тип/имя, но не меняет ветку. Сервис повторно использует переименованный worktree, если ключ присутствует в задаче; фактический тип проверяет агент, а не backend.

Результат через MCP обязателен. Структурированный итог: статус, описание, ссылки, артефакты, проверки. Ошибки остаются в текущей колонке с дополнительной меткой. Прерванные запуски не повторяют внешние действия автоматически. Хранить сообщения, сессии, версии профилей и историю. Восстановление сессии или новая с контекстом из базы.

## MCP
list_boards, list_tasks, get_task, create_task, report_progress, post_message, request_clarification, submit_result. Временные полномочия по запуску/роли, без прямого доступа к БД. Нельзя менять чужой результат или устаревшую версию.

Для общего браузера — acquire_resource/release_resource с автоматическим освобождением после завершения или отмены запуска. Итог сначала сохраняется, а стадия меняется только после выхода процесса. При недоступной сохранённой сессии пользователь может сбросить ID без автоматического повтора и затем продолжить с историей задачи.

Агент создаёт задачи на любой доске сразу в низ To Do, с родителем и происхождением. Дедупликация внутри доски по нормализованным описанию и необязательному источнику (включая Done). Разные описания одного тикета разрешены. Нормализация только переводов строк и внешних пробелов. Создание атомарное. Для расписаний отдельная уникальность слота.

## Расписания
На каждой доске таблица шаблонов. Интервал — дни+часы, положительный. Сетка от даты начала; дни недели фильтруют без сдвига. Каждый слот создаёт экземпляр независимо от предыдущего. Время означает enqueue. Зона Europe/Moscow по умолчанию. Простой — пропуски в истории без массового catch-up. Уникальность template+slot. Предпросмотр ближайших запусков.

## Навыки
Единый каталог `src/GigaTodo/AgentConfig/catalog.json`: 32 навыка, 21 условный сценарий, восемь профилей и три политики разрешений. Матрица сохраняется в snapshot запуска и передаётся через prompt, agent-profile.json и локальный GIGACODE.md. Шаблоны восьми named agents, permissions и документация генерируются `scripts/export-agent-config.py`; `--check` проверяет отсутствие расхождений. Эти шаблоны не запускают дополнительных исполнителей. Скрипты run-app.sh и link-extension.sh подготовлены; подключение в реальном CLI выполняется отдельно.

Расширение приложения: task-execution, task-decomposition, task-critique, task-feedback, frontend-development. Общие инструкции + роль + задача, с сохранением GIGACODE.md/AGENTS.md проекта. Личные навыки ~/.gigacode/skills; проектные .gigacode/skills. Пользовательские глобальные настройки не переписывать. Учитывать paths и disable-model-invocation.

Переиспользовать openspec-context (первым), один полный вход OpenSpec, artifacts-check/roast, apply, ksupbim-review, test-runner, pr-plan, Pixso-пару, ru-text/check/score и skill-builder по назначению. Полные инструкции ещё нужно проверить. Обычным задачам OpenSpec не навязывать; состояние по внутреннему ID; архив отдельно после своих условий. Существующие подтверждения сохраняются.

Подключить проверенную закреплённую версию Superpowers: systematic-debugging, verification-before-completion, requesting/receiving-code-review, test-driven-development, brainstorming, writing-plans. Без второго диспетчера, дублирующих OpenSpec-планов и управления worktree. Узкие помощники возвращают результаты родителю.

Frontend skill: изучение дизайна, локальный запуск, API/dev-proxy, SberBrowser devtools, сценарии/консоль/сеть, сравнение с макетом, исправления и отчёт. API КСУП БИМ: https://ksup-bim.ift.delta.sbrf.ru/bim/api (переопределяемый параметр репозитория). Не коммитить локальные доступы. Общий браузер блокировать; скриншоты в файлы. Недоступный стенд — не успешная проверка.

При отсутствии CLI/доступа тесты красные, без skip/Mock; независимый запуск Category!=RealGigacode сохраняет локальный набор приложения. Проверка всего внешнего окружения остаётся отдельной.

## P12 — React и Pixel Agents
- Полный перенос досок, форм, зависимостей, обсуждений, результатов, расписаний, настроек и SSE на React.
- Режимы «Доски» / «Офис», один C#-диспетчер. Canvas-движок и графика Pixel Agents закреплены на commit b1bafd02896d90d83457266575a1e8e5011ce997 под MIT, с LICENSE и SHA256 файлов.
- Read-only /api/office: запуски всех досок, роль, статус; без credentials и полных CLI-журналов. SSE запускает обновление снимка, polling восстанавливает обновления.
- 20 мест на этаж; до 100 активных агентов и до 20 недавних завершённых. Завершённые видны не более 45 секунд; отдельные метки Mock и критика. Нажатие открывает карточку.
- Отсутствие связи явно показывается, анимация приостанавливается. Список запусков доступен с клавиатуры и на телефоне.
- Анимация отражает состояние процесса и роль; вызовы инструментов и внутренние субагенты Gigacode не визуализируются без подтверждённого формата событий.
- Приёмка: production build, целостность vendor, распределение 100 агентов, API без секретов, регрессия досок в браузере, офис desktop/mobile, ошибки графики и связи. Реальная CLI-приёмка отдельно.

## P13 — .NET 8
- Приложение и тесты: net8.0, C# 12; global.json выбирает SDK 8.0. Решение GigaTodo.sln совместимо с SDK 8.
- EF Core 8.0.33, Npgsql provider 8.0.11, Npgsql 8.0.9; согласованные runtime-пакеты в приложении и тестах. Инструмент dotnet-ef 8.0.33 закреплён локальным manifest.
- Применённые миграции и данные сохраняются. Текущий snapshot соответствует EF Core 8; исторические ProductVersion в старых migrations не переписываются. Смена runtime не требует отката или пересоздания базы.
- Приёмка на SDK 8: restore/build без warnings, все локальные тесты на чистом PostgreSQL, отсутствие pending model changes, browser и process/HTTP smoke; запуск с существующей базой просмотра. CLI Gigacode проверяется отдельно, без подмены реальной интеграции.

## P14 — Вложения задач и расписаний
- Отдельная кнопка «Прикрепить файлы»: любые типы, несколько за загрузку, оригиналы сохраняются. Загрузка до создания/сохранения исключает запуск задачи без её вложений.
- Метаданные в PostgreSQL, файлы в Runtime:Root/attachments. UUID-ссылки задач/шаблонов; экземпляры расписания наследуют ссылки атомарно. Изменение шаблона не затрагивает старые экземпляры. Удаление связи не удаляет общие материалы.
- SharpCompress 0.50.8 на .NET 8: ZIP/RAR/7z/TAR и сжатые варианты, вложенные архивы, список содержимого и скачивание. Парольные/повреждённые/неполные/неподдерживаемые архивы получают явный Failed; исходник сохраняется, частичная распаковка удаляется.
- Размер загрузки, суммарная распаковка, число элементов, вложенность и время ограничены настраиваемыми Attachments__*. Нельзя выходить за папку, создавать ссылки/спецфайлы, перезаписывать извлечённые файлы или исполнять вложения при загрузке.
- Изменять набор нельзя во время активного запуска; версия и board lock защищают изменения. Дедупликация задачи сохраняет новые вложения. ID входных файлов сохраняются в snapshot запуска.
- Оригиналы, SHA256, статус, ошибка и пути к содержимому доступны агенту через prompt, attachments.json и MCP get_task. Агент использует инструменты по формату; недоступное чтение/распаковка не считается успешным.
- Проверки: форматы и вложенность, traversal/ссылки/лимиты, привязка/дедупликация/расписания/конкурентные стадии в PostgreSQL, UI upload/download/add/remove/mobile и чтение вложения процессной фикстурой через MCP. Настоящий Gigacode проверяется отдельно.
