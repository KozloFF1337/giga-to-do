# План: навыки по выбору задачи и эксклюзивный sberchat-analyst

Дата: 2026-11-07. Статус: спецификация подготовлена, реализация не начата.
Стек сохраняется: .NET 8, PostgreSQL, React. Содержимое двух пользовательских навыков не изучается и в проект не копируется. Интеграций с мессенджерами в backend не добавляется.

## 1. Поведение для пользователя

В форме новой задачи добавить раздел «Дополнительные навыки» со списком из двух независимых флажков:

| ID | Подпись | Назначение | Ограничение параллельности |
|---|---|---|---|
| `gigacode-chat` | Отправлять информацию о сессии в чат | Использовать существующий пользовательский навык | Дополнительного ограничения нет |
| `sberchat-analyst` | Общаться с аналитиками | Использовать существующий пользовательский навык | Не более одной выполняющейся задачи на всех досках |

Оба флажка по умолчанию выключены. Можно выбрать любой набор, включая пустой и оба навыка. Это дополнение к существующей матрице навыков, а не её замена. Выбор разрешает применение навыка по назначению; существующие инструкции навыка и разрешения роли определяют порядок работы.

Выбранные ID сохраняются у задачи и показываются в её карточке. Политика действует для всех её сессий: исполнитель, критик и ответ исполнителя. Флажок не расширяет права роли: критик по-прежнему проверяет результат, а ExecutorReply только отвечает. Автоматическое исправление кода или разрешение всех внешних действий из флажка не следует.

До первого запуска выбор можно менять в To Do при отсутствии активного run, с проверкой версии. После первого запуска набор фиксируется: чтобы изменить его, создаётся новая задача. Это исключает возобновление старой сессии с разрешениями, которые пользователь уже снял. В Done флажки только для чтения.

В форме повторяющейся задачи добавить тот же список. Каждый новый экземпляр получает копию выбранных ID. Изменения шаблона относятся только к будущим экземплярам.

## 2. Значение «не использовать без галочки»

Разрешённые ID задаёт backend из сохранённого выбора задачи. Промпт, ссылка на навык, сообщение пользователя/агента или наличие навыка в глобальном окружении сами по себе не включают эти два навыка.

Нужно обеспечить два уровня:

1. Формирование профиля: выбранные навыки включаются в эффективную конфигурацию и инструкции сессии; остальные из этой пары явно выключены. Ни один сценарий каталога, инструкция доски или сгенерированный named agent не должен включать их в обход выбора.
2. Загрузка в CLI: выключенные навыки исключаются из обнаружения/вызова конкретной сессии средствами установленного Gigacode. Одного удаления ID из agent-profile.json или запрета в тексте недостаточно.

Перед реализацией второго уровня проверить возможности форка по его документации/настройкам, не читая содержимое этих навыков. Не придумывать поддерживаемые CLI-флаги. В имеющемся конспекте `disable-model-invocation` описывает запрет автоматического вызова, но сам по себе оставляет ручной вызов; это ещё не полная изоляция.

Использовать подтверждённые настройки исключения навыков для конкретного процесса. Если их нет — реализовать и проверить изолированную конфигурацию загрузчика для сессии, сохранив доступ к авторизации и прочим пользовательским навыкам/MCP. Глобальные файлы пользователя не изменять, навыки на диске не переименовывать и не удалять. Простая подмена HOME без проверки загрузки авторизации и MCP не подходит.

Если форк не позволяет обеспечить запрет, показывать явную ошибку конфигурации и не запускать реальную сессию с неподтверждённым ограничением. Не выдавать только prompt-запрет за выполненное требование. Если выбранный навык не установлен, также сообщать об ошибке, не снимать флажок молча.

Ограничение относится к этим навыкам и их вызовам. Изоляция всех потенциальных эквивалентных действий через произвольный shell/MCP — отдельная задача; не отключать общие инструменты, нужные другим навыкам. При делегировании внутренним субагентам должна наследоваться та же политика пары навыков; это подтвердить в целевой приёмке.

## 3. Данные и API

Предлагаемые изменения:

- `WorkItem.OptionalSkillIds`: PostgreSQL text[], по умолчанию пустой массив.
- `Recurrence.OptionalSkillIds`: тот же тип, копируется при создании экземпляра.
- `CreateTaskRequest`, `ScheduleRequest`: необязательный `optionalSkillIds`, отсутствие означает пустой массив.
- Отдельный версионный запрос изменения выбора до первого запуска, например `POST /api/tasks/{id}/optional-skills`.
- `AgentRun.ExclusiveSkillKey`: nullable text; для запуска задачи с `sberchat-analyst` — `sberchat-analyst`, иначе null.
- Snapshot запуска: выбранные ID, эффективная политика обоих навыков, эксклюзивный ключ и версия политики. Runtime/resume читает snapshot, а не изменяемую текущую конфигурацию задачи.

Список допустимых ID фиксирован и проверяется backend. Удалять повторы, сохранять канонический порядок; неизвестные ID отклонять. Старые задачи и шаблоны после миграции получают пустой выбор. Не включать навыки по умолчанию при обновлении.

Учитывать существующую дедупликацию по доске/описанию/источнику: если найденная задача имеет другой набор optionalSkillIds, вернуть понятный 409 с ID найденной задачи. Не менять её разрешения и не терять выбор молча. Для изменения использовать явное редактирование, если оно ещё разрешено. При совпадающем наборе сохранить существующее поведение дедупликации/вложений.

MCP `get_task` возвращает выбор и эффективную политику. Для агентского `create_task` новые задачи по умолчанию получают пустой набор, без автоматического наследования. Агенту запретить самостоятельно включать эти два навыка для дочерней задачи: непустой запрос отклоняется, включение запрашивается у пользователя. Пользовательский выбор в расписании, напротив, является разрешением для его будущих экземпляров.

## 4. Общая блокировка sberchat-analyst

Блокировку назначает backend до запуска CLI, а не агент после вызова навыка. Она применяется ко всем ролям запуска задачи с этим флажком, даже если конкретная роль не воспользовалась навыком. Блокировка распространяется на все четыре доски и экземпляры расписаний в одной БД приложения.

Использовать существующую транзакцию `Dispatcher.Claim` и общую PostgreSQL advisory-блокировку назначения. Дополнительно создать частичный уникальный индекс по `AgentRun.ExclusiveSkillKey` для строк с непустым ключом и состоянием Running. Сейчас enum хранится числом и Running = 0; SQL-фильтр миграции должен соответствовать реальному отображению EF. Уникальный индекс защищает инвариант и при ошибке в диспетчере.

Алгоритм назначения:

1. В существующей транзакции проверить общий лимит `Runtime__MaxConcurrentAgents` и лимит роли доски.
2. Определить, занят ли активным run ключ `sberchat-analyst` на любой доске.
3. Сохранить действующий порядок очереди и правила зависимостей; дополнительно исключить кандидатов с этим навыком, если ключ занят. Применять фильтр **до** выбора первой задачи, в обеих ветках назначения — executor и review/reply.
4. Взять следующую доступную задачу. Если она с флажком — создать Running run с эксклюзивным ключом в той же транзакции, что меняет состояние задачи.
5. Если сработал уникальный индекс, откатить назначение целиком; не запускать CLI и не оставлять InWork без run. Повторить выбор на следующем тике, не считать это ошибкой задачи.

Ожидающая ключа задача остаётся в очереди, не занимает слот агента и не получает постоянный Blocker, который потребовал бы ручного «Продолжить». UI показывает вычисляемую причину ожидания и ссылку на задачу-владельца. Когда ключ свободен, ожидание исчезает автоматически.

Блокировка держится весь активный запуск, включая ожидание разрешённых внешних инструментов и backend-восстановление авторизации с resume. Сохраняется тот же run и тот же ключ. `submit_result` сам по себе ключ не освобождает: сначала должен завершиться процесс CLI и его дерево, затем финализироваться run.

При успехе, ошибке, подтверждённой отмене или прерывании Running меняется на конечное состояние, и ключ становится доступен. TTL/истечение bearer-токена сами по себе не освобождают ключ живого процесса. В InReview с ожиданием человека, паузе без процесса или между отдельными запусками ключ не удерживается: эксклюзивность относится к фактическому выполнению, а не ко всему жизненному циклу карточки.

При рестарте нельзя освободить ключ и запустить вторую задачу, пока старый дочерний CLI ещё жив. При реализации проверить текущую очистку процессов, остановку дерева и восстановление Interrupted; при невозможности подтвердить завершение оставить запуск заблокированным с понятной диагностикой. Проверить также смену режима и падение backend. Существующей записи Failed/Interrupted без контроля процесса недостаточно для доказательства эксклюзивности.

Для `gigacode-chat` эксклюзивный ключ не создаётся. Задачи с ним и без дополнительных навыков работают параллельно в рамках общего лимита 1–100. Задача с обоими навыками занимает один слот и один ключ. Для Mock применять тот же механизм очереди, чтобы его можно было проверить без пользовательских навыков. Внутренние субагенты не получают отдельного слота, но относятся к запуску-владельцу и не должны переживать его завершение.

## 7. Проверки при реализации

1. Пустой выбор, каждый отдельный навык и оба вместе; сохранение/чтение; неизвестный ID; миграция старых записей; запрет изменений после первого запуска и при конфликте версии.
2. Дедупликация с одинаковым и разным выбором, Done-дубликат без скрытого изменения; агентское создание без выбора и отклонение саморазрешения; наследование расписанием без изменения старых экземпляров.
3. Два конкурентных назначения на разных досках: одновременно Running только один run с ключом. Проверить executor, critic, ExecutorReply и защиту уникального индекса независимо от диспетчера.
4. Сверху ждёт задача с занятым ключом — следующая допустимая задача запускается. Проверить вместе с зависимостями, лимитами доски и общим лимитом; ожидание ключа не расходует агентский слот.
5. Освобождение после успеха/ошибки/отмены, отсутствие освобождения на одном лишь submit_result или TTL, удержание при auth-recovery, пауза/ручное ревью без процесса, аварийный рестарт с живым дочерним процессом.
6. Смена роли, доработка, ответ и resume сохраняют выбранную политику; выключенный навык не возвращается из старой сессии или шаблона named agent. Обычная матрица остальных навыков продолжает работать.
7. UI: флажки, редактирование расписания, фиксированный набор после старта, ожидание и снятие метки, мобильный экран; существующие проверки завершённых задач сохраняются.
8. На реальном Gigacode проверить discover/invocation двух навыков для всех четырёх наборов, в том числе после resume и внутреннего делегирования. Содержимое навыков не переписывать. Для фактической проверки отправки сообщений использовать согласованный пользователем тестовый чат.

Сейчас выполняется только подготовка плана: код, миграции, тесты и реальные внешние действия в рамках этого документа не запускаются. Локальная CLI-фикстура при реализации подтвердит доставку политики и протокол, но не фактическую работу пользовательских навыков и мессенджеров.
